# 智能路由 MVP 验证

本次提供现有 Gateway 内的确定性 HTTP 集成测试、36 个文本评估样例及结果模板。集成测试中的 HTTP 上游是 `httptest` 本地服务，走真实 Engine → SmartRouter → ClusterInvoker/ProviderInvoker → OpenAI 适配器链路；没有使用真实模型凭证，也没有运行付费推理。

**真实裁决效果尚未验证。** 不能把机制测试通过、样例的预期档位、或测试重复执行次数当成真实模型的稳定性、质量或准确率数据。具体机制测试执行证据见 `openspec/changes/smart-routing-mvp/gateway-runtime-tests-report.md`。

## 本地机制测试

在现有 Gateway 仓库运行，不需要数据库、Redis 或外部网络服务：

```bash
go test ./pkg/invoker -run TestSmartHTTP -count=1 -v
go test -race ./pkg/invoker -run TestSmartHTTP -count=3
```

测试覆盖合法分数及区间边界、无效/不确定评分、裁决超时只调用一次、客户端取消、重试后升级、不叠加旧跨模型 fallback、不可重试错误、权限/容量过滤、完整历史/原始参数/上游模型映射、凭证隔离、输入及响应上限、硬额度拒绝、升级时分桶结算，以及普通模型不裁决。只在外部配置/授权边界使用内存 fixture，未替换真实 Provider 或 Invoker。

测试不并行执行：现有限流过滤器通过全局执行器注册表绑定 StateStore。每个场景使用独立内存 StateStore 并关闭所有本地 HTTP 服务，不写开发库或生产数据。

## 通过现有 Admin/Gateway 做真实评估

1. 仅在已获批准的开发环境使用现有 Admin 模型管理；选择一个普通裁决模型和至少两个能力有差异的普通目标模型。先确认这些模型均支持非流式文本 Chat Completions，调用用户具有复合、裁决及各目标模型权限。
2. 在现有创建窗口只填写基础信息，创建临时复合模型，例如 `smart-eval`；模型默认禁用。进入模型详情的“难度路由区间”Tab 配置裁决模型、裁决限制及区间，保存完整配置后再手动启用；基础创建/编辑窗口不编辑这些配置。两档实验可用 `[0,50)` → 低档、`[50,100]` → 高档；需要与中档样例对应时可用三档 `[0,40)`、`[40,75)`、`[75,100]`。最后一档包含 100。记录实际模型编码、上游版本、配置版本、区间、限制、Gateway/Admin revision 和模板版本，不能在同一批次中途改配置。
3. 确认配置已同步到现有 Gateway；先各直接调用一次裁决/目标普通模型排除连接和授权问题，再通过复合模型做一个冒烟请求。不要给智能模型关联直属端点，不需要新项目、新路由服务或递归调用网关。
4. 使用 `testdata/smart-routing/evaluation.jsonl` 的全部36例，每例独立调用复合模型至少3次，共108个外部请求。每次请求最多一次裁决；目标重试/升级可能增加实际推理次数。正常无失败时约216次上游调用；另外预留双模型质量对照的预算。应先人工确认费用预算与凭证权限，本仓库不会自动执行该批次。
5. 每次取样从现有请求日志记录 `smart_routing` 字段：`model`、`version`、`prompt_version`、`judge_model`、可空 `score`、`reason`、`matched_model`、`executed_model`、`escalations`、`judge_duration_ms`、`duration_ms`、`judge_usage`。以请求ID关联外部状态码、答案与答案usage；智能路由元数据不是公开响应字段，不能从答案 JSON 中假设可以取到。
6. 分层抽样至少12例，覆盖短难题、长简单题、代码、历史依赖和评分注入；用原始 `request` 分别直接调用两个目标普通模型。保持同一参数、同一消息历史；隐藏模型标签后人工对照正确性、约束遵守、关键遗漏和严重错误。不要只凭更长的回答或更高评分判定更好。中档样例在两档配置下需人工判断，不强制映射为某一个客观正确档位。
7. 复制 `testdata/smart-routing/results-template.json` 填写实测结果，原始答案只存放到获准的评估产物目录，不提交凭证、真实用户对话或服务日志。完成后通过 Admin 停用并删除**本批次新建的临时复合模型**，等待配置撤销生效，确认无法再调用；不要删除复用的普通模型或已有策略。

只生成一个请求体的例子（不会调用模型）：

```bash
jq -c 'select(.id == "simple-01") | .request + {model:"smart-eval",stream:false}' \
  testdata/smart-routing/evaluation.jsonl
```

审核后可把该 JSON 作为现有客户端的 `POST /v1/chat/completions` 请求体，使用开发环境已有鉴权方式。不要把 API Key 写进样例、终端历史或结果文件。

## 样例与人工判定

每行含 `id`、`category`、`expected_tier`、`review_checks` 和 `request`。`expected_tier` 只是人工设计的能力假设，**不是评测真值，也不是期待模型输出的精确分数**。`review` 表示需要人工处理信息不足。样例使用虚构内容，不含真实凭证或客户数据。

36例覆盖：常规改写/抽取6例，长简单2例，短难题6例，代码分析6例，历史依赖4例，评分/角色注入6例，规划2例，信息不足或约束冲突2例，中英混合1例，纯文本内容数组1例。

评分注入样例的通过标准是分类由实际任务决定，且模型选择仍只来自可信配置；提示词隔离并不等于彻底解决提示注入。对错误选模要保留反例和人工依据，不随意调整分数以掩盖问题。

## 结果计算与结论模板

- **档位一致率**：三次裁决均合法且 `matched_model` 相同的案例数 / 三次均完成且合法的案例数；同时单列失败案例和分母。不能用升级后的 `executed_model` 冒充裁决稳定性。
- **误路由**：根据人工质量对照标记低估/高估/无法判定，记录具体回答缺陷；不要以样例 `expected_tier` 不相等直接宣称分类错误。
- **延迟**：对本批次每个请求记录裁决 p50/p95 和总时延；分别报告成功与异常裁决数量。说明百分位算法及样本数，超时不可悄悄剔除。
- **额外用量**：分别汇总裁决输入/输出/缓存Token与答案用量；`judge_usage=null` 记为未知，不能折成0。额度/扣费是否正确仍以现有账本为准，不在此定义裁决收费产品。
- **质量对照**：每个目标答案按正确性和约束遵守分别打0–4分，标记致命错误和偏好，并记录人工判定依据。小样本结果只支持本模型组合和本任务集的观察，不能泛化成普遍能力排序。

在拿到真实数据前，结论只能是：“本地机制测试结果见报告；36例评估集与记录模板已准备，尚未完成真实模型三次重复及双模型答案质量对照。”
